# web3d-M6 plan: one engine

**Opened:** 2026-10-01 (after M7 closed; M5 parked before its live runs)
**Milestone:** web3d-M6 ([pivot note](2026-09-27-web3d-pivot.md), M6 row)

**Exit criteria:**
1. **No `macroquad` in `Cargo.toml`.**
2. **Every example runs on the kernel,** natively and in the browser.
3. **`twec build` produces a desktop `.exe` for 3D games,** as it already does for 2D.

## Where things stand

There are two runtimes:
- **2D** (44 examples): `twec play` on macroquad. Its window loop lives in `src/play.rs`, as four near-copies (file, embedded, wasm, headless-ish). The draw builtins in `src/stdlib.rs` call macroquad directly, about 190 call sites: shapes, text and fonts, sprites and atlases, tilemaps, nine-slice panels, UI widgets, `fx`, `light2d`, `camera2d`.
- **3D** (12 examples and `survive3d`): the wgpu kernel (`src/kernel/`), with a native winit shell (`src/play3d.rs`) and a WebGPU shell (`crates/twe-web`). In 3D, `rect` and `text` already queue `HudItem`s, which the kernel draws as a screen overlay (`src/kernel/hud.rs`).

Most of what macroquad does for 2D already has a non-macroquad path from the 3D shells:
- audio: `audio_host`, through quad-snd natively and WebAudio in the browser;
- windows and input: winit;
- gamepads: gilrs;
- the clipboard: arboard.

What M6 really replaces is 2D drawing and the 2D window loop.

## Method

**A reference before anything changes.** Session 1 captures every 2D example's frame under macroquad, at fixed frames with fixed input. Every later session compares the kernel's frames against those references with a pixel-difference score, not by eye. The references are kept even after macroquad is deleted.

**One draw path.** Every 2D draw builtin pushes a command into one list. The list is drawn by the kernel, both as a 2D game's whole frame and as a 3D game's overlay. Each kind of drawing exists once.

## Sessions

1. **The draw-command list, and references.** *Done 2026-10-01 ([note](2026-10-01-web3d-m6-session1.md)).*
   - Every 2D draw builtin pushes a `Draw2d` command (replacing `HudItem`).
   - macroquad replays the list, and 2D games are pixel-identical.
   - A `TWE_CAPTURE=frame:path` hook in `twec play` captures the reference screenshots: 74 frames of 37 examples. The first capture found 13 examples blank (fixed).
2. **The kernel's 2D canvas.** *Done 2026-10-02 ([note](2026-10-02-web3d-m6-session2.md)): 31 of 37 examples render on the kernel within 0.36 mean difference of their references; the other 6 wait for widgets.* `hud.rs` grows into `kernel/canvas.rs`:
   - tessellated shapes and outlines, lines;
   - TTF text at any size;
   - textured sprites with atlas frames and tint;
   - the `camera2d` transform (and what a screen shake does with no camera; see the session 1 note).

   3D overlays gain every primitive. Headless render tests, and the first comparisons against the references.
3. **The native 2D shell.** *Done 2026-10-02 ([note](2026-10-02-web3d-m6-session3.md)), with the UI widgets pulled forward from session 5: all 74 reference frames through the real window within a mean of 1.12; `TWE_PLAYER=macroquad` keeps the old loop until session 6.* `twec play` runs on winit and the kernel, with everything `play.rs` provides:
   - input (keys, mouse, text input, gamepad);
   - pause and focus, F3 and F12;
   - hot reload, crash reports, replays, audio through `audio_host`.

   The comparison covers all 44 examples.
4. **The browser.** `twec build --target web` builds 2D games on `twe-web`. The macroquad wasm build is removed.
5. **The rest of the 2D surface:**
   - ~~UI widgets~~ (session 3), `fx`, `light2d`, tilemaps, nine-slice panels (session 2: they draw through the list);
   - touch, the clipboard;
   - `play_visual`.

   Every example compared.
6. **Delete macroquad:**
   - the dependency and the four play loops;
   - `twec build` embeds the kernel runtime for 3D games too.
7. **Closeout.**

## Rules for this milestone

- **Commits:** `web3d-m6:`. Closeout note at the end.
- **No new script surface.** M6 changes the runtime underneath. Every builtin keeps its signature and its meaning, and a difference against the reference is a bug unless the note explains it (for example, font antialiasing).
- **The 640×480 virtual canvas stays** (see the M3 HUD), letterboxed to the window.
- **Tests and docs as always:** clippy clean for native, wasm32 and `twe-web`; `docs/06` §7 where behaviour is documented.
