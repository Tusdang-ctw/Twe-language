## What shipped

Twenty tasks in three tiers, listed in `bench/README.md`:

| Tier | Kind | Tasks |
|---|---|---|
| 1 | Logic and timing | `move_player`, `countdown`, `score_combo`, `health_regen`, `traffic_light`, `ammo_reload`, `day_night` |
| 2 | Entities and state | `coin_collect`, `enemy_chase`, `spawner_waves`, `projectile_fire`, `bomb_radius`, `door`, `pause_menu` |
| 3 | Input-driven play | `dash_cooldown`, `jump_gravity`, `click_move`, `xp_magnet`, `survivor_mini`, `snake_grid` |

**Each task's files:**
- **`task.md`** describes behaviour in language-neutral words, with every number a check depends on: speeds, durations, radii, orders, edge cases ("pressing R during a reload does nothing").
- **`twe.md`** names what the checks read: top-level `var`s, and entity classes with a `pos` field. Scene variables aren't reachable from top-level code, so the interface never lives inside a scene.
- **Checks** sit at least a few ticks away from the events they test, so an implementation that updates a tick earlier or later still passes.

**Validation:** all 20 tasks validate (`twec bench check --all`). All 137 checks are failed by running mutants of their solutions: at least 2 each, 17.8 on average.

**An independent cross-check.** For `enemy_chase`, `xp_magnet` and `survivor_mini`, whose numbers are hard to derive by hand, the check values come from a separate Python simulation of the task text. The Twe solutions, written independently, agree with it on every event.

**A pilot of the task text (not a benchmark result).** A Claude subagent wrote all 20 programs from only `task.md`, `twe.md` and the primer, without seeing the solutions or checks. It had `twec verify`, `twec run` and a harness of its own for input, and no limit on attempts.
- **All 20 of its programs pass**, although it made different choices at every point the text leaves open: whether the press tick also advances time, the update order within a tick, `<` against `<=` at radii. The checks hold up against those choices.
- **The ambiguities it listed are recorded.** Tightening them changes no check.
- **The tasks may be easy for a frontier model with unlimited tools.** The benchmark gives a model at most 4 rounds and no input harness. If v0 still doesn't separate languages, session 6's harder tier has to.

**Grader changes:**
- **The mouse persists:** a span's `mouse` position holds until the next span that sets one, as a real mouse's does. Before, it read (0, 0) between spans.
- **`tier`** (1–3, default 1) is read from `task.toml` for the scorecard.

## Findings for later (no language change during M5)

- **`spawn` is a statement and gives no handle**, so code can't set a field on the instance it just made. `survivor_mini`'s solution passes the bolt's direction through a top-level `aim`. If models trip on this in the runs, it's a candidate language change after M5.
- **Scene variables can't be read from outside the scene** (`Game.score` is an error). For the benchmark this only shapes the interfaces. For games it means shared state must be top-level, which the primer already says.
- **Stdlib names shadow undeclared globals in probes** (`label` is a UI builtin; session 2).
- **From the pilot** (fixed before any measurement; see the next commit):
  - `twec verify` accepts `return` inside an `on update` handler, and `.len()` on a list. Both fail at run time.
  - The primer's entity example (`on update(dt):` and `self.pos` inside an entity) doesn't parse.
- **Also from the pilot** (left as they are):
  - summing `dt` drifts (90 ticks give 1.4999999999999996), so exact-second thresholds need a tolerance;
  - `twec run` has no way to feed input.
