# 2026-04-29 — v0.2 session 2b: function-body `wait`

## Status: shipped. Second of three sessions on the function-body `wait` track. Builds on 2a's resumable `if` / `while` blocks (`docs/changes/2026-04-29-v0.2-session-2a-resumable-blocks.md`); 2c brings the bytecode VM to parity.

## Background

Session 2a replaced `Instance::entry_resume_index: Option<usize>` with `entry_resume_path: Vec<PathEntry>` so `wait` could fire inside `if` / `elif` / `else` / `while` blocks at the top of a state's `on_entry` body. The path-based machinery was scoped to a single body: function calls still went through `eval_stmt` → `run_block` → "wait is only supported at..." error.

Session 2b lifts that limit by reifying the call stack. `Instance::fiber_frames: Vec<Frame>` now holds one `Frame` per active body — bottom is the state's `on_entry`, top is whichever function call is currently suspended. `wait` works at any depth in any of those frames.

## What ships

### Frame stack

`src/value.rs`:

```rust
pub struct Frame {
    pub kind: FrameKind,
    pub resume_path: Vec<PathEntry>,
}

pub enum FrameKind {
    StateEntry,
    Function {
        def: Rc<FunctionDef>,
        saved_returning: Option<Value>,
        saved_params: Vec<(String, Option<Value>)>,
    },
}

pub struct Instance {
    // ...
    pub fiber_frames: Vec<Frame>,  // was: entry_resume_path: Vec<PathEntry>
    pub entry_wait_remaining: f64,
    // ...
}
```

`fiber_frames[0]` is the bottom of the stack; `fiber_frames[len-1]` is the top. `Vec::push` / `Vec::pop` manage the top naturally. State-entry is always at index 0; function frames sit above it in call-stack order.

`Function`'s embedded `saved_returning` / `saved_params` are the env state shadowed by the function's parameter bindings at call entry. Restored when the frame finishes (whether it completes immediately or after a wait+resume cycle).

### Push-before-run convention

`run_state_entry` and `run_user_call_resumable` both push their frame onto `fiber_frames` *before* running the body, then update the frame's `resume_path` in place on suspend or pop the frame on completion. This keeps the stack ordered correctly even when a deeper call suspends mid-body — that deeper frame lands on top of the running frame, not below it.

### Resumable function-call dispatch

`is_top_level_user_call(env, expr)` decides whether a `Stmt::Expr(expr)` is a candidate for the resumable path. v0.2 session 2b restricts it to bare-name calls whose target resolves to a user-defined `Value::Function`:

- Self-method calls (resolved via `find_method` on `self`'s class) — fall through to `eval_stmt`. Method-body wait deferred.
- `recv.name(args)` with `Expr::Field` callee — deferred (same reason).
- Builtins, `apply_call` of a stored Value::Function — deferred.
- Calls in expression position (`let x = f()`) — deferred. Needs a way to carry the return value back into the parent runner after a resume; non-trivial.

`run_user_call_resumable` mirrors `call_function`'s param-binding (positional + kwarg → reordered Vec via `bind_kwargs`), then drives the body through `run_block_resumable`. On suspend it leaves the function frame in place with its updated `resume_path`. On completion it pops the frame and restores `env.returning` / parameter shadowed bindings from the saved fields.

### Resume-fiber loop

`resume_fiber` now drives the topmost frame in place (snapshots `kind` + `resume_path`, runs the body, updates path on suspend, pops on completion). The loop drains frames bottom-down: when a function frame completes, the next iteration resumes the parent frame — which may complete in turn, or hit another suspendable stmt and re-suspend.

Function frames get the `env.call_depth += 1` / `-= 1` bracket inside the loop so `return` inside the function body remains valid mid-resume.

### Tests

5 new tests in `tests/eval.rs`:

- `wait_in_function_program_runs` — drives the on-disk `tests/programs/wait_in_function.twe` (committed reference for the function-body wait surface).
- `wait_inside_function_called_from_state_entry_resumes` — basic case.
- `wait_inside_function_inside_if_resumes` — function call sits inside an if-then; two frames on the stack at suspension time.
- `two_sequential_waiting_calls_run_in_order` — back-to-back calls each with their own wait. Three frames over the test's lifetime.
- `function_calls_function_with_wait` — `outer()` calls `inner()` which waits. Three frames simultaneously suspended; resume drains innermost-first.

`wait_in_function_called_from_outside_state_still_errors` replaces the prior `wait_outside_state_body_still_errors_in_function` — same intent (calling a wait-bearing function from top-level remains an error since there's no fiber context to suspend into) but with a name that reflects the new capability boundary.

### `tests/programs/wait_in_function.twe`

Real Twe program with a chain state that calls a `delay()` function twice in sequence, plus a transition. The `delay` function declares before the scene so the binding is in place when `enter_state` fires.

## Not in scope

Deferred to follow-on sessions:

- **Method-body wait.** Self-method calls and `recv.method()` calls fall through to `eval_stmt`. Same pattern as functions but needs `FrameKind::Method { recv, def }` and self-binding on resume.
- **Call-as-expression with wait.** `let x = f()` where `f`'s body waits requires a way to pipe the return value back into the parent runner's expression evaluator after the resume. Non-trivial — likely a parent-side "expecting value at path P" annotation.
- **`for`-body wait.** Iterator-state preservation; `Branch::For { iter_index: usize }`. Mostly mechanical, just hasn't been needed yet.
- **Bytecode VM parity.** The VM's `OpCode::Wait` saves a single `(chunk, IP)` on `BcInstance` — single-frame, like the pre-2a tree-walker. Session 2c lands the equivalent frame stack for `--vm bytecode`.
