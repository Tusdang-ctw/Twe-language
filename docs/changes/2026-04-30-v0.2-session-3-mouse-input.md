# 2026-04-30 — v0.2 session 3: mouse input

## Status: shipped. Closes the "mouse input" line item from `docs/05-roadmap.md` Phase 8 (v0.2 — Foundations for shipping). Ships on both backends (`twec play` macroquad + `twec play3d` winit).

## Background

v0.1 shipped keyboard input via `key.<name>` (continuous) and `key_press.<name>` (edge-triggered). Mouse was deferred per `docs/changes/2026-04-29-phase-5-closeout.md` and re-confirmed as a Phase 8 item in the v0.2-v1.0 roadmap. UI primitives in Phase 10 will need mouse hover + click; this session unblocks that line of work without prejudging the UI design.

## What ships

### Twe-side surface

Three new ambient Objects, parallel to `key` / `key_press`:

```twe
mouse.x          # f64 — cursor X in pixels
mouse.y          # f64 — cursor Y
mouse.pos        # tuple (x, y) — convenience for builtins that take a position
mouse.wheel      # f64 — accumulated wheel delta this frame (reset each frame)

mouse_held.left   # bool — true while the button is held
mouse_held.middle
mouse_held.right

mouse_press.left  # bool — true only on the frame the button transitions to down
mouse_press.middle
mouse_press.right
```

Edge-triggered semantics on `mouse_press` mirror `key_press`: useful for "open menu on click" handlers that should fire once per press, not once per held frame. `mouse_held` is for "drag while held" patterns.

### `src/stdlib.rs`

`install` now seeds the three Objects with default-zero values. Both backends update them each frame; programs run before the first frame see zeroed mouse state, not undefined.

### `src/play.rs` (macroquad / `twec play`)

- `MOUSE_BUTTONS` constant: `&[("left", MouseButton::Left), ("middle", MouseButton::Middle), ("right", MouseButton::Right)]`. Same name set as `play3d`.
- `write_mouse_object(target)`: pulls `mouse_position()` + `mouse_wheel()` and writes into the `mouse` Object.
- `write_mouse_buttons(target, pred)`: predicate-driven button-state writer. Same function services both `mouse_held` (predicate `is_mouse_button_down`) and `mouse_press` (predicate `is_mouse_button_pressed`).
- `update_key_state` (tree-walker path) and `update_vm_input` (bytecode VM path) both call the new helpers.

### `src/play3d.rs` (winit / `twec play3d`)

`App` gains:

- `mouse_x: f64`, `mouse_y: f64` — cursor position from `WindowEvent::CursorMoved`.
- `mouse_wheel_y: f32` — accumulated this frame from `WindowEvent::MouseWheel`. `LineDelta` and `PixelDelta` are normalized to the same line-delta scale (`pixel.y / 120.0` is the conventional approximation).
- `mouse_buttons_held: HashSet<&'static str>`, `mouse_buttons_pressed_this_frame: HashSet<&'static str>` — same shape as `keys_held` / `keys_pressed_this_frame`.

Three new `WindowEvent` arms in `App::window_event`:

- `CursorMoved` — overwrite `mouse_x` / `mouse_y`.
- `MouseInput { state, button }` — `Pressed` adds to held + pressed-this-frame; `Released` removes from held only.
- `MouseWheel { delta }` — accumulate y-axis component into `mouse_wheel_y`.

`update_mouse_state(env, mouse_x, mouse_y, wheel_y, held, pressed)` writes into the env each frame, then the App resets `mouse_wheel_y = 0.0` and `mouse_buttons_pressed_this_frame.clear()`.

### Cross-backend parity

Buttons surfaced: `left`, `middle`, `right`. macroquad doesn't expose `Back` / `Forward` / `Other`; winit does, but they're filtered out so cross-backend Twe code reads the same set.

Wheel scaling: macroquad's `mouse_wheel()` returns "tick" counts where each notch is roughly 1.0; winit's `LineDelta` matches this directly, and `PixelDelta` is divided by 120 (the conventional Windows mouse-wheel "delta-per-tick"). Twe scripts read a single `mouse.wheel` number that's roughly comparable across both.

### Tests

3 new tests in `tests/eval.rs`:

- `stdlib_installs_mouse_objects` — pin the field shape (`mouse.x` / `.y` / `.pos` / `.wheel`; `mouse_held.{left,middle,right}`; `mouse_press.{left,middle,right}`).
- `mouse_position_drives_on_update_logic` — write `mouse.x` between frames, accumulate via `on update(dt):`. Verifies the Object is reachable from a tick.
- `mouse_press_left_drives_branching` — three frames (press / no-press / press), expect `clicks == 2`. Edge-triggered semantics held.

The actual winit / macroquad event handling is exercised manually via the example program.

### Example

[examples/mouse_demo.twe](../../examples/mouse_demo.twe). Cursor-following circle that grows on hold and shifts hue on click; wheel changes the base radius. Hits all three Objects in one short program. Runs under `twec play`.

## Not in scope

- **`mouse_release`** edge surface. Same family as the deferred `key_release` (Snake's NP1). Defer until 3+ user reports want it.
- **Cursor visibility / lock / capture**. `cursor.hide()`, `cursor.lock()` for FPS-style relative input. Phase 9 / 10 territory.
- **Touch input**. Mobile / tablet. Off the v1.0 critical path.
- **Mouse wheel x-axis (horizontal scroll)**. Surfaced only as `mouse.wheel` (y-axis); horizontal wheel is rare and reserved for future without breaking the current API.
