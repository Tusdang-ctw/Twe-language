# 2026-04-29 — v0.2 session 2a: resumable `if` / `while` blocks

## Status: shipped. First of three sessions on the function-body `wait` track. 2a refactors `run_state_entry`'s flat-integer resume into a path-based runner; 2b adds frame-stack call resume; 2c brings the bytecode VM to parity.

## Background

Phase 5 task 2 shipped `wait <duration>` as a direct child of a state's `on_entry` body. The runner walked the body's statements with an `Option<usize>` "next-stmt index" stored on the Instance; `Stmt::Wait` was intercepted before reaching `eval_stmt`. Anything that hit `eval_stmt` (`run_block` for `if` / `while` / `for` bodies, function calls, `every` clocks) errored with "wait is only supported as a direct statement of a state body in v0.1."

The closeout note (`docs/changes/2026-04-29-phase-5-closeout.md`) listed function-body `wait` as a v0.2 carry-over with an explicit cost note: "needs CPS or heap-allocated call frames." We picked heap-allocated frames and staged the work across three sessions:

- **2a (this one):** Refactor the state-entry runner to a path-based resumer. Same external behavior at depth 1; new capability at depth 2+ within `if` / `while`.
- **2b:** Push a frame on function calls. Function-body `wait` works.
- **2c:** Bytecode VM parity (its current `OpCode::Wait` is single-frame too).

## What ships

### Path-based resume

`src/value.rs`:

```rust
pub struct PathEntry {
    pub stmt_index: usize,
    pub branch: Option<Branch>,
}

pub enum Branch {
    IfThen,
    IfElif(usize),
    IfElse,
    While,
}

pub struct Instance {
    // ...
    pub entry_resume_path: Vec<PathEntry>,  // was: entry_resume_index: Option<usize>
    pub entry_wait_remaining: f64,
    // ...
}
```

Path semantics:

- `path[0]` describes the body the entry frame is rooted in (always the state's `on_entry` in 2a).
- `path[k+1]` describes the sub-body reached by descending through `path[k].branch` from `path[k].stmt_index`.
- The last entry always has `branch == None` and its `stmt_index` is the next statement to execute on resume.
- An empty path means "not suspended."

`IfElif(idx)` records which arm matched at suspension time — resume picks the same arm without re-evaluating elif conditions, so side-effecting predicates run exactly once per logical branch entry.

### Resumable runner

`src/eval.rs`:

- `run_state_entry(env, scene, stmts, incoming_path: &[PathEntry])` replaces the previous `start_at: usize` signature. Calls `run_block_resumable`, captures the result, stores or clears `entry_resume_path` on the Instance.
- `run_block_resumable(env, scene, body, incoming, out_path)` — the core. On the first iteration, may drill into a sub-block guided by `incoming[0].branch`. Subsequent iterations are fresh executions. On `wait` or sub-block suspension, builds `out_path` innermost-first; the caller of `run_state_entry` reverses once for storage.
- `run_while_resumable(env, scene, cond, body, drilling, inner_incoming, out_path)` — the loop wrapper. First iteration may drill (resume mid-body); subsequent iterations re-evaluate `cond` and run the body fresh.
- `FiberOutcome` enum: `Completed | Suspended | Returning | Breaking | Continuing | Transitioning`. Mirrors the env-flag based control-flow signalling but separates Suspended (no env-flag analogue) so the path-building logic is explicit.

What remains routed through `eval_stmt`:

- `for` loops. Iterator-state preservation needs more design; `for` bodies still surface the original "wait is only supported at..." error via `run_block` if a wait is reached.
- Function and method calls. The frame stack lands in 2b.
- `every` clocks, `on update`, `dialogue`, `Stmt::Expr(call)`. Same story — they go through `run_block`.

## Not in scope (deferred to 2b / 2c)

- **`for` body resume** — needs iterator-index preservation. The `Branch::For { iter_index: usize }` extension is straightforward but needs a design pass on what happens when the iterable is mutated mid-iteration.
- **Function-body `wait`** — needs a `Vec<Frame>` on the fiber rather than a single root path. Each function call pushes a frame; `wait` saves the entire stack; `return` pops; resume replays innermost-out.
- **Bytecode VM parity** — the VM's `OpCode::Wait` saves chunk + IP on `BcInstance` (single frame). Same refactor pattern: a `Vec<BcFrame>` on the fiber.
- **`wait` inside `dialogue` / `every` / `on update`** — these all currently error. `dialogue` needs a per-dialogue scheduler (separate design). `every` and `on update` are fire-and-forget by design and probably stay that way.
- **`break` / `continue` resume across a wait inside a while** — currently works at the level of "body completes naturally before re-evaluating cond," but `break` / `continue` *fired during* a sub-block whose wait suspended would lose the signal across the suspend. Edge case; revisit if reported.
