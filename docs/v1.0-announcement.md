# Twe v1.0 — A game language that ships games

*This is the draft announcement post for when v1.0 releases publicly. The codebase is ready; the itch.io ship and community reviews are the remaining external criteria.*

---

We're shipping Twe v1.0 — a scripting language built from scratch for 2D game development, with one design constraint above all others: **game concepts are first-class language constructs, not library calls**.

```twe
entity Slime:
    var pos = (0.0, 0.0)
    var hp = 3

    function update(dt):
        # chase the player
        let dx = player_x - pos.x
        let dy = player_y - pos.y
        let d = math.sqrt(dx*dx + dy*dy)
        pos = (pos.x + dx/d * 40.0 * dt, pos.y + dy/d * 40.0 * dt)

    function render():
        rect(at: (pos.x - 10, pos.y - 10), size: (20, 20), color: color.cyan)

on Slime.death(s):
    spawn Spark at (s.pos.x, s.pos.y)
```

`entity`, `state`, `visual`, `dialogue`, `particles`, `scene` — these are Twe keywords, not class names you inherit from or interfaces you implement.

## The proof

The v1.0 thesis is: **a developer can ship a Vampire-Survivors-class commercial 2D game on Twe**. So we built one.

`examples/survive_beta/` is a 1300-line Vampire-Survivors clone: arena-based movement, wave-spawned enemies (slimes, bats, skeletons, a boss), auto-attack projectiles, orbiting blades, a damaging aura, XP drops and magnetic collection, a level-up upgrade picker, a full pause menu, settings save/load across launches, gamepad support, and a build pipeline that produces a self-extracting Windows `.exe` with no Twe install required on the target machine.

It was dogfooded — played, broken, fixed — before shipping. The first playtest session caught two real engine bugs (modal-state transitions were silently discarded; the window was rendered in the top-left of a mismatched surface on HiDPI displays) that the test suite couldn't catch because they only fire under live render + mouse input. That's what "dogfood" means.

We also built a second game: `examples/rpg_demo/` — a small dialogue-driven adventure with rooms, an NPC with branching conversation, key pickup, chest interaction, and persistent save-load. It exercises the RPG pillar of the design that the Survivors clone doesn't touch: `dialogue` blocks, scenes-as-rooms, settings as game flags.

## What's in the box

| Layer | What |
|-------|------|
| **Language** | Indentation-based syntax, `let`/`var`, 0-indexed arrays, only `false` is falsy, string interpolation, tuples, lists, ranges, if-expressions |
| **Game constructs** | `entity`, `state`, `scene`, `dialogue`, `particles`, `visual` |
| **Type system** | Three-tier: non-strict default → `# strict` → `# verified` (JSON output for LLM self-correction) |
| **2D runtime** | `twec play` — macroquad, 640×480, rect/circle/line/text/sprite/atlas/font drawing, mouse/keyboard/gamepad |
| **3D runtime** | `twec play3d` — wgpu, cubes/spheres/`.glb` meshes, WASD, Lambertian lighting |
| **Visual runtime** | `twec play_visual` — `visual` block → WGSL compilation → wgpu (procedural fire, noise-based shaders) |
| **Build** | `twec build` — bundles assets, zstd-compresses, produces self-extracting Windows `.exe` |
| **Tooling** | `twec fmt`, `twec types`, `twec verify` (LLM JSON), `twec profile` (Chrome trace), `twec lsp`, tree-sitter grammar, VS Code extension |
| **Modules** | `import` + multi-file projects with `twe.toml` |
| **Steam** | `--features steam` build: `achievement.unlock`, `stat.set/get`, `cloud.save/load` |

## Why not Lua?

The honest version is in `docs/03-runtime.md`. The short version: Lua gives you no entity lifecycle, no state machines, no typed vectors, no structured error messages that suggest fixes. Every Lua-embedded engine reinvents all of those and the reinventions diverge. Twe's answer is to bake the game primitives into the language once, correctly.

Why not GDScript? GDScript is good but it's tied to Godot. Twe's runtime is the engine — there's no host engine to be tied to. And Twe is designed for LLM authorship as a first-class audience alongside humans (predictable grammar, structured diagnostics, `# verified` mode that produces machine-parseable JSON), which GDScript isn't.

## AI-legible by design

Twe was designed for two audiences simultaneously: humans who want a game running quickly, and language models that generate code. Every design choice serves both.

- **Predictable LL(1)-ish grammar.** No context-sensitive parsing; no "is this a type or a value?" ambiguity.
- **Structured diagnostics.** Every error has a `suggested_fix`. `twec verify` emits JSON the LLM can act on without parsing error strings.
- **Round-trippable AST.** `twec parse` emits a stable JSON AST. Tooling can read and write Twe programs without a hand-rolled parser.
- **Three-tier type system.** Non-strict runs everything. Strict catches provable mistakes. Verified produces annotated JSON a model can self-correct against.

## Getting started

```
cargo install --git https://github.com/your-org/twe-language twec
twec play examples/pong.twe
```

The tutorial in `docs/tutorial.md` walks through building Pong from scratch (Part I: language basics → Part II: Pong → Survivors → mini-RPG). New contributors target building Pong from the tutorial in under two hours.

## What's next

v1.x will follow a 12-month LTS policy: security and critical fixes backport; public surface changes require a `@deprecated` cycle before removal. The first milestone post-v1.0: a second shipping game by a community author.

3D polish (animation, physics, multi-primitive `.glb`), multiplayer, macros — all post-v1.0, intentionally. Twe v1.0 is the smallest language that can ship a Steam-class 2D game. That's the whole bet.
