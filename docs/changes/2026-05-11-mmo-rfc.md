# MMO architecture RFC — sharded zones + replicated entities

**Status:** accepted-with-deferrals 2026-05-11. Gate for Phase 41 sessions 2 onward.

**Parent:** `docs/05-roadmap.md` Phase 41.

## Question

Phase 41 is the roadmap's explicit ceiling — "MMO / Roblox-scale 3D
foundation." The roadmap entry already flags the size:

> Multi-year, post-v2.0 territory. The ceiling. Extends Phase 32's
> Tunic-scale open world to persistent-world / massively-shared-
> world. ... whether Twe ever opens it is a future-implementer
> decision.

The hard question: **given this phase cannot realistically ship its
server runtime as a single-maintainer effort, what can land in the
open-source repo today that doesn't lie to authors about the project's
ambitions?**

## Decision

Phase 41 ships **architecture + abstraction stubs**, not a runtime.
Concretely:

1. **An architecture RFC** (this document) that picks one model
   among the three alternatives and explains the trade-offs.
2. **Author-facing API stubs** (`mmo.replicate`, `mmo.persist`,
   `mmo.broadcast`, `mmo.entities_near`) that compile + run today
   as **single-player no-ops**. Scripts that use them work as
   ordinary single-player games; when (if) a server runtime
   appears, the same scripts gain multi-player behaviour without
   author changes.
3. **A `examples/mmo_demo/`** that demonstrates the API call sites
   in a runnable (single-player) game.
4. **Honest deferral of the runtime.** No server code ships. The
   exit criterion "100 concurrent players on a $20/month VPS" stays
   open until a future-implementer-with-bandwidth opens the phase
   properly.

The motivation: future-proof the API. Today's `mmo_demo` is a one-
player simulation, but when an MMO runtime lands the same Twe source
keeps working. The roadmap's "the ceiling" framing stays honest —
this phase is genuinely deferred — but it's not silently deferred.
There's a concrete API contract on disk that future work has to
honor or break explicitly.

## Architecture choice: sharded zones

The three alternatives the roadmap lists:

1. **Sharded servers.** World is split into named zones; each zone
   runs on a separate server process. Players cross zone boundaries
   via explicit "travel" handoffs (loading screens / portals). Easy
   to scale: spin up new shards as load increases. Trade-off:
   visible zone boundaries.
2. **Seamless world.** Players move freely through a unified world;
   server uses spatial partitioning to balance load. Trade-off:
   harder to scale; load imbalances create hot-spot servers; player
   migrations between server boundaries are continuous and error-
   prone.
3. **Instanced zones.** Each player or party gets its own instance
   of a zone (Diablo / Path of Exile / Destiny model). Easy to
   scale per-instance; trade-off: not a "shared world" in the MMO
   sense.

**Pick: sharded servers.** Rationale:

- Smallest engineering surface. Sharding lets each zone be a
  separate server process; the only cross-server coordination is
  player-transfer handoffs.
- Aligns with Phase 32's spatial structures. Each shard's world is
  the Phase 32 `WorldSpatial` + chunked streaming machinery
  unchanged; the only additions are server-side
  serialisation + cross-shard handoffs.
- The "loading screen between zones" trade-off is familiar to MMO
  players (WoW + FFXIV + GW2 all use it) and forgiveable.
- Migrations between server boundaries (the seamless-world trade-
  off) are the single largest engineering risk in MMO architecture;
  shards sidestep that risk entirely.

Instanced zones get a follow-on hook (`mmo.create_instance(name)`)
but are not the v1.x default — Twe is positioned as a "shared
persistent world" platform if anyone opens Phase 41 properly.

## Author-facing API

```twe
# Tag an entity's state as replicated. Per the Phase 37 precedent
# (rollback opt-in via rollback.snapshot calls), scripts manually
# call mmo.replicate(name, value) for each field that should sync.
# Parser sugar `entity Player: replicated = true` is a v1.x ergonomic
# pass item.
entity Player:
    var x = 0.0
    var y = 0.0
    var z = 0.0
    var health = 100

    on update(dt):
        x += vx * dt
        z += vz * dt
        mmo.replicate("player.x", x)
        mmo.replicate("player.z", z)
        mmo.replicate("player.health", health)

# Persist state to the server-side database. The key is the
# replication key; the value is serialised via canonical-JSON.
mmo.persist("player.x", x)
let saved_x = mmo.load("player.x")

# Broadcast a one-shot event to peers in the same shard (chat
# messages, dropped items, party invites, etc).
mmo.broadcast("chat", "Hello, world!")

# Read incoming broadcasts (drains the queue; each event observed once).
let evt = mmo.next_event()    # → {channel, sender_id, payload} or nil

# Area-of-interest queries: which entities are near (x, y, z)?
# Composes with Phase 32's `world.spatial_query_radius`.
let nearby = mmo.entities_near(x, y, z, radius)

# Sharding lifecycle.
mmo.shard_id()                # → "default" today; the active zone name
mmo.transfer_to(shard_name)   # request a zone handoff (no-op locally)
```

The contract reads like a single-player simulation today: `mmo.persist`
saves to local storage, `mmo.replicate` is a no-op, `mmo.broadcast`
fires events that only the local script receives, `mmo.entities_near`
falls through to `world.spatial_query_radius`. When a server runtime
lands, the same calls route through the network — scripts don't
change.

## What the runtime would look like (sketch)

This section is non-binding sketch. A future-implementer-with-
bandwidth would re-RFC + re-design before opening Phase 41 properly.

- **Server-authoritative.** Distinct from Phase 31 lockstep + Phase
  37 rollback (those are peer-to-peer). Server holds the canonical
  state; clients send inputs + receive snapshots.
- **Area-of-interest networking.** Server only sends per-tick
  updates for entities within the player's AOI radius (~50m default,
  per-zone-tunable). 1000-entity zones with 100 players send maybe
  20 entities per player per tick, not 1000.
- **Persistent world database.** Snapshot ring buffer that flushes
  to a SQL store (SQLite for small shards, PostgreSQL for big ones,
  Redis for hot cache) every N ticks. `mmo.persist(key, value)`
  goes through the same buffer.
- **Cross-shard handoffs.** Player transfers between shards via a
  dedicated handoff service — the source shard serialises the
  player's state, the destination shard deserialises + spawns.
  Loading-screen UX.
- **Player-authored code sandboxing.** If Twe ever runs adversarial
  player code on shared servers (Roblox-class), the sandbox needs
  CPU/memory limits + capability-restricted stdlib + gas metering.
  See the separate "sandboxing pre-requirements" document
  (`docs/changes/2026-05-11-mmo-sandboxing-pre-reqs.md`) for the
  hardening checklist.
- **Workshop / mod APIs.** First-class user-generated-content
  publishing — out of scope for v1.x; tracked as a Phase 41 sub-
  component if anyone opens it.

## What this RFC does *not* settle

- **The server runtime itself.** The whole runtime is honest-deferred.
- **VPS / cloud cost model.** Out of scope until a real runtime
  exists.
- **Anti-cheat for server-authoritative games.** The roadmap's
  Phase 31 RFC scoped out anti-cheat for peer-to-peer; server-
  authoritative shifts the model but doesn't eliminate the cheating
  surface. Out of scope here.
- **Open-source vs hosted offering.** Whether the eventual MMO
  runtime ships open-source or as a hosted service (or both) is a
  future-implementer business decision.

## Open questions (deferred, not answered here)

Quoting the roadmap entry:

- Does Twe extend to a server-hosted multi-tenant runtime, or stay
  author-side / engine-side only? — **Deferred.**
- How does the language's no-macros / no-metaprogramming locked
  decision survive MMO needs (replication attributes, network-tier
  annotations)? — **Deferred.** The current model uses runtime
  builtin calls (`mmo.replicate`) rather than language-level
  attributes; that may need to change.
- Sandboxing — can the existing `unsafe_code = "deny"` discipline
  scale to running adversarial player code? — **Deferred.** See
  `docs/changes/2026-05-11-mmo-sandboxing-pre-reqs.md`.

## Exit criteria for Phase 41

Per `docs/05-roadmap.md` Phase 41:

- `examples/mmo_demo` supports 100 concurrent players on a single
  $20/month VPS. **(Honestly deferred — no server runtime ships.)**
- Player-authored Twe code can be published, sandboxed, and run on
  the server without compromising other tenants. **(Honestly
  deferred — sandboxing is a separate v3.0+ effort.)**

Codebase-side exit (what this phase actually ships):

- This RFC.
- Author-facing `mmo.*` API stubs (8 builtins) — compile + run
  today as single-player no-ops.
- Sandboxing pre-requirements document.
- Workshop / mod API trait stubs.
- `examples/mmo_demo/` single-player simulation using the API.
- Closeout enumerating what's deferred and why.
